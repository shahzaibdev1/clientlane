# Optional client accounts and two-way invitations

Approved scope from conversation: clients bring existing providers; freelancers/agencies also invite clients. No marketplace. Existing provider workspace and optional client import remain usable; anonymous private links remain supported.

Clients optionally authenticate using existing Supabase Auth. A client dashboard lists only explicitly accepted project relationships across studios, displays next actions, and opens an authenticated client-only project view supporting the existing response/upload/feedback/decision/quote/deadline/handover features. No internal notes, workspace controls, other clients, or team permissions leak. Account relationships are separate from bearer grants: either can be independently revoked, and deletion/replacement must not transfer access.

Provider owners invite the email belonging to a project's client, preview/copy a secure expiring invitation and optionally send via existing SMTP queue. Confirmed invited email must accept before access exists. Owner can revoke pending invites and accepted access. Clients can create a project brief and invite an existing provider email. Acceptance by that confirmed provider atomically creates a project/client in their owner workspace and links its originating client. Pending briefs do not grant workspace access. Repeated acceptance cannot duplicate projects. Recipients can decline; sender can revoke. Fresh invitations after revocation may restore access deliberately. Invite tokens hashed, no broad credentials in browsers; validate email/title/brief/dates and safe return destinations.

One identity may use both studio and client views. Signup offers clear client/studio entry options without overwriting identity metadata to infer authorization. Keep default provider login/workflow intact and offer explicit navigation between views. Client accounts free in product wording, no billing setup or plan enforcement added. Honest empty/loading/error states, mobile readable, accessible dialogs, noindex/private no-store/referrer behavior for all account/invitation routes.

Builder choices: separate relational capability tables/RPCs, focused service/action modules and client dashboard component. Preserve current large components with narrow integration edits. All DB changes additive, existing local data/environment retained. Test actual authorization, recipient/expiry/revocation/delete/stale-accept races and two complete real browser invitation workflows. No external email, deployment or payments during development.
